# План интеграции с InvenTree

Цель: быстро наполнить InvenTree (https://p2ptd-inventory.online) базовым инвентарём по райдерам заведений, а потом упростить поддержку данных: распознавание оборудования по фото и автоматическое добавление мануалов в карточки.

## Общая архитектура

Всё работает через REST API InvenTree с помощью официальной библиотеки `inventree` (Python). Скрипты лежат в этом репозитории и запускаются локально или по расписанию.

```
райдеры (PDF/DOCX/XLSX) ──► парсер ──► review.yaml ──► загрузчик ──► InvenTree
                                          ▲  (проверка человеком)
фото оборудования ──► распознавание ──────┘
карточки Part ──► поиск мануалов ──► вложения (ссылка или PDF)
```

Принципы:

* **Идемпотентность.** Любой скрипт можно запускать повторно. Деталь ищется по паре «производитель + модель», позиция склада по паре «деталь + место хранения» (или по серийнику). Существующее не дублируется, а обновляется.
* **`--dry-run` у каждого скрипта.** Сначала смотрим, что будет создано, потом пишем в базу.
* **Человек между распознаванием и записью.** Всё, что получено автоматически (из райдеров, фото, поиска мануалов), проходит через промежуточный файл, который можно поправить руками.
* **Секреты не в репозитории.** URL и API-токен InvenTree, ключ Claude API берутся из `.env` (в `.gitignore`).

Структура репозитория:

```
inventory/
  client.py            # подключение к InvenTree, общие хелперы (get_or_create)
  catalog.py           # нормализация названий, справочник производителей и алиасов
scripts/
  create_categories.py # дерево категорий (уже готов, перенести сюда)
  create_locations.py  # заведения и места хранения (уже готов, перенести сюда)
  parse_riders.py      # этап 1: райдеры → review.yaml
  import_stock.py      # этап 1: review.yaml → Part + StockItem
  photo_bot.py         # этап 3: распознавание по фото
  attach_manuals.py    # этап 4: мануалы
data/
  riders/              # исходные райдеры (не коммитим, если там чувствительные данные)
  review/              # промежуточные YAML после парсинга
  aliases.yaml         # «A&H» → «Allen & Heath», «SQ5» → «SQ-5» и т. п.
```

## Этап 0. Подготовка (0,5 дня)

1. Перенести в репозиторий `create_categories.py` и скрипт мест хранения, вынести общий код в `inventory/client.py`.
2. Создать в InvenTree отдельного пользователя-бота с API-токеном и правами на Part, Stock, Company.
3. Завести производителей как компании (Company, флаг Manufacturer). Модель хранить через Manufacturer Part (MPN), чтобы потом искать мануалы и сверять фото по точному коду модели.
4. Договориться о формате названия детали: `Производитель Модель` (например, `Allen & Heath SQ-5`), IPN не используем или генерируем автоматически.

## Этап 1. Базовый инвентарь из райдеров (2–3 дня)

Райдер описывает, что *должно* стоять в заведении, без серийников. Поэтому из него получается черновик склада, который потом подтверждается при обходе.

**1.1 Извлечение текста.** PDF через `pdfplumber` (сканы через OCR), DOCX через `python-docx`, XLSX через `openpyxl`.

**1.2 Структурирование.** Текст отправляется в Claude с жёсткой JSON-схемой ответа. На выходе по каждой строке райдера:

```yaml
venue: "Заведение 1"
items:
  - raw: "Пульт цифровой Allen&Heath SQ5 - 1 шт"
    category: "Звук / Микшерные пульты / Цифровые"
    manufacturer: "Allen & Heath"
    model: "SQ-5"
    quantity: 1
    location: "Заведение 1 / Сцена"     # если в райдере есть привязка к зоне
    confidence: high
    note: ""
```

Категория выбирается только из существующего дерева (список категорий передаётся в запрос), так что модель не придумает новую ветку. Позиции с низкой уверенностью помечаются для ручной проверки.

**1.3 Нормализация.** Словарь `aliases.yaml` приводит разные написания одной модели к одному виду, чтобы `SM58`, `Shure SM-58` и `SM 58 Shure` стали одной деталью. Словарь пополняется по ходу.

**1.4 Проверка.** Вы просматриваете `data/review/<заведение>.yaml`: правите категорию, модель, место хранения, удаляете лишнее. Это быстрее, чем вносить вручную, и это единственный ручной шаг.

**1.5 Загрузка** (`import_stock.py`):

* создать Manufacturer и Part (если нет) в нужной категории, Trackable для техники с серийниками;
* создать StockItem с количеством из райдера в месте хранения заведения;
* пометить позицию статусом «Требует внимания» (Attention needed) и примечанием «из райдера, не проверено», чтобы при обходе было видно, что ещё не подтверждено.

**1.6 Обход и серийники.** На месте сотрудник открывает позицию, сверяет и через действие *Serialize stock* превращает «4 шт SM58» в 4 позиции с серийниками (или оставляет количество, если серийников нет). Статус меняется на OK. После этого печатаются QR-этикетки.

Отчёт о расхождениях: скрипт выводит по каждому заведению, что из райдера ещё не подтверждено, чтобы было видно прогресс обхода.

## Этап 2. Этикетки (0,5 дня)

Шаблон этикетки InvenTree для StockItem: логотип, модель, серийник, заведение, QR со ссылкой на позицию. Печать пачкой по месту хранения.

## Этап 3. Парсер фотографий (3–5 дней)

Задача: сфотографировал шильдик или сам прибор, получил распознанные производитель, модель, серийник, а запись в InvenTree создаётся или обновляется в пару нажатий.

**Распознавание.** Claude (vision) получает фото и список известных моделей и возвращает JSON: производитель, модель, серийный номер, категория, уверенность. Серийник с шильдика читается хорошо, поэтому основной сценарий именно фото шильдика; общий вид прибора полезен для картинки карточки.

**Интерфейс.** Рекомендую Telegram-бота, а не плагин InvenTree:

* сотрудники уже на месте с телефоном, ставить ничего не надо;
* сценарий: выбрать заведение и место (кнопки) → отправить фото шильдика (и, по желанию, общий вид) → бот показывает распознанное и находит в InvenTree совпадение → кнопки «Создать / Привязать к существующей / Исправить»;
* если в месте есть неподтверждённая позиция из райдера с той же моделью, бот предлагает именно её сериализовать, так обход по этапу 1.6 идёт через бота;
* доступ только для белого списка Telegram ID.

**Что записывается:**

* общий вид прибора ставится картинкой детали (Part image), если её ещё нет;
* фото шильдика прикладывается вложением к позиции склада (StockItem attachment);
* серийник, место, статус OK.

Альтернатива без бота: папка фото (Google Drive) и пакетный скрипт, который делает такой же `review.yaml`, как в этапе 1. Подходит для разовой загрузки архива фотографий.

## Этап 4. Мануалы в карточках (2–3 дня)

Мануал относится к модели, поэтому прикладывается к детали (Part), а не к каждой позиции склада.

**Поиск** (`attach_manuals.py`), для каждой детали без мануала:

1. Справочник источников по производителям (`data/manual_sources.yaml`): у многих брендов предсказуемые страницы загрузок (Allen & Heath, Shure, Yamaha, Behringer, Chauvet, Epson и т. д.). Это самый надёжный путь.
2. Если справочник не помог, веб-поиск по запросу `"<производитель> <модель>" user manual filetype:pdf`.
3. Найденные кандидаты проверяются: скачивается первая страница PDF, Claude подтверждает, что это руководство именно к этой модели (а не к соседней в серии), и определяет язык.

**Запись:**

* по умолчанию вложение-ссылка (link attachment) на официальный PDF с комментарием «Руководство пользователя (EN)»;
* по флагу `--download` PDF скачивается и прикладывается файлом, чтобы мануал был доступен без интернета и не пропадал при смене сайта производителя;
* у детали ставится параметр `manual_status = found / not_found / manual`, чтобы повторные запуски не искали заново и было видно, где нужен ручной поиск.

Скрипт запускается после импорта и далее по расписанию (раз в неделю) для новых деталей.

## Порядок работы и что нужно от вас

| # | Шаг | От вас |
|---|-----|--------|
| 0 | Подготовка репозитория и API | API-токен пользователя-бота (в `.env`, не в чат); скрипт мест хранения |
| 1 | Импорт по райдерам | Райдеры всех заведений; соответствие «заведение → места хранения» |
| 1.6 | Обход и серийники | Люди на местах |
| 2 | Этикетки | Логотип, размер этикеток и модель принтера |
| 3 | Фото-бот | Решение: Telegram-бот или пакетная обработка; где будет крутиться бот |
| 4 | Мануалы | Решение: ссылки или скачивать PDF |

Для этапов 1, 3 и 4 нужен ключ Claude API (расход на разовую обработку райдеров и мануалов небольшой).

## Открытые вопросы

1. В каком формате райдеры (PDF, Word, Excel, сканы)? От этого зависит извлечение текста.
2. Если одна позиция райдера описана без модели («радиомикрофон — 2 шт»), заводим обезличенную деталь вида «Радиосистема (модель не указана)» или пропускаем до обхода?
3. Какая версия InvenTree? Модель вложений поменялась в 0.16 (общий `/api/attachment/`), скрипты подстроятся, но лучше знать заранее.
